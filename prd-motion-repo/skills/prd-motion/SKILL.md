# PRD → 기능별 모션그래픽

PRD는 사람마다, 제품마다 다르다. 이 스킬의 목표는 어떤 PRD가 와도 **기능 하나하나가 "이 기능이라서 이렇게 움직인다"고 납득되는 장면**을 만드는 것이다. 예쁜 파티클을 깔고 기능 이름만 바꿔 끼우는 결과물은 실패다.

결과물은 스크롤 기반 단일 HTML 페이지 하나다. 영상 AI나 외부 토큰은 쓰지 않는다. 모션은 전부 Canvas 2D, SVG, CSS로 만든다.

## 작업 순서

### 1. 기능 인벤토리 만들기 (가장 중요)

PRD를 끝까지 읽고, 기능마다 아래 항목을 채운 표를 먼저 만든다. 코드는 이 표가 다 채워진 뒤에 쓴다. 표가 비어 있으면 장면이 기능을 반영하지 못하고 장식이 된다.

| 항목 | 질문 | 예 (공항 PRD의 FR-02) |
|---|---|---|
| ID·이름 | PRD에 적힌 그대로 | FR-02 실시간 혼잡도 예측 및 경보 |
| 핵심 동사 | 이 기능은 무엇을 하는가? | 예측한다, 경보한다 |
| 바뀌는 양 | 이 기능이 동작하면 **어떤 숫자나 상태가 바뀌는가?** | 구간별 예상 대기 시간, 경보 여부 |
| 대상 | 화면에서 움직일 실체는 무엇인가? | 구간(카운터 A, 보안 G, H), 대기 인원 |
| Before → After | 기능이 없을 때와 있을 때 무엇이 다른가? | 혼잡을 모름 → 임계치 넘으면 즉시 경보 |
| 사용자 입력 | 사용자가 조작하는 값은 무엇인가? | 경보 임계치 |
| 출력 | 그 결과 무엇이 보이는가? | 경보 목록, 권고 인원 |
| PRD 데이터 | Mock data, 예시 수치, 데모 시나리오 | 보안 H 112명 24분 |
| 의존 관계 | 다른 기능의 출력을 쓰는가? | FR-01 데이터 필요, FR-04에 결과 전달 |

PRD에 수치가 없으면 숫자를 지어내지 말고 상대적인 크기(막대 길이, 점 개수)로 보여 주거나, 꼭 필요하면 `예시` 라벨을 붙인다. PRD에 Mock data나 데모 시나리오가 있으면 그 값을 그대로 쓴다. 보는 사람이 "우리 PRD의 그 숫자"를 알아봐야 한다.

**계산에 필요한 값이 PRD에 없을 때**: 조작하면 결과가 계산되어야 하므로 건별 속성(금액, 좌표, 결과 준비 시각 등)이 필요할 때가 많다. 이때는 다음처럼 한다.
- PRD 총계나 예시값에 정확히 맞도록, 시드를 고정한 예시 분포를 만든다(`MK.seeded`). 예를 들어 405건의 유형별 건수를 PRD 표와 같게 맞춘다.
- 모델의 기준점은 PRD 예시값에 맞춘다. 공항 예시에서는 보안 H가 24분이었고, 병원 예시에서는 X-ray가 12분이었다. 기본 상태에서 화면 숫자가 PRD 데모 시나리오와 같게 나와야 한다.
- 지어낸 값은 섹션 캡션에 "무엇이 예시인지" 한 줄로 밝힌다.

**Before를 정의할 때**: PRD가 기존 방식을 적었으면 그대로 쓴다(예: "오더지 순서대로 번호표", "전 건 팀장 승인"). 적지 않았으면 가장 단순한 현행 관행으로 정하고 화면에 이름을 붙인다(예: 균등 배분, 요청 순서대로 배정, 예약순). Before가 일부러 나쁘게 설계되면 안 된다. 보는 사람이 "지금 우리가 하는 방식"이라고 느껴야 한다.

### 2. 기능마다 모션 유형 고르기

`references/archetypes.md`를 읽고, 1단계 표의 **핵심 동사와 바뀌는 양**을 기준으로 기능마다 유형을 고른다. 고르는 기준은 이렇다.

- 유형은 기능 이름이 아니라 **바뀌는 양의 모양**으로 고른다. "AI 추천"이라도 바뀌는 양이 "후보가 줄어든다"면 분류(Sort) 유형이고, "자원이 옮겨간다"면 재배치(Rebalance) 유형이다.
- 한 페이지 안에서 같은 유형이 반복되면 장면이 서로 구분되지 않는다. 두 기능이 같은 유형에 걸리면, 둘 중 하나는 두 번째 후보 유형으로 바꾸거나 같은 유형이라도 대상과 레이아웃을 확실히 다르게 만든다.
- 여러 기능에 걸친 대표 가치(대기 제거, 비용 절감 등)는 히어로 장면 하나로 보여 준다. 히어로는 PRD의 핵심 가치 문장을 그대로 시각화한다.

고른 결과는 스토리보드 표로 사용자에게 먼저 짧게 보여 준다. 사용자가 바로 진행하라고 했거나 요청이 분명하면 표를 보여 준 뒤 그대로 진행한다.

| 기능 | 모션 유형 | 무엇이 움직이나 | 사용자가 조작하는 것 | 보이는 결과 |
|---|---|---|---|---|

### 3. 시각 세계를 PRD 도메인에서 가져오기

색과 형태는 그 제품의 현장에서 가져온다. 공항이면 게이트 표지와 출발 안내판, 병원이면 차트와 활력징후 모니터, 물류면 송장 라벨과 바코드, 금융이면 체결 시세판, 제조면 공정 라인과 안돈 표시등처럼 정한다. 정하는 방법과 예시는 `references/visual-worlds.md`에 있다.

- 토큰으로 정의한다. 배경, 패널, 선, 글자, 흐림 글자, 강조색 1개, 그리고 의미 색 3개(정상, 주의, 위험)를 정한다.
- 의미 색은 장면 안에서 상태 변화를 보여 주는 데만 쓴다. Before는 위험이나 주의 색, After는 정상 색으로 바뀌는 식이다.
- 한글이 들어가는 고정폭 글꼴에는 반드시 한글 대체 글꼴을 붙인다. 예: `'JetBrains Mono','IBM Plex Sans KR',monospace`. 빠뜨리면 한글이 깨져 보인다.

### 4. 페이지 구성

`assets/skeleton.html`을 출발점으로 쓴다. 공통 헬퍼(보일 때만 돌아가는 루프, 캔버스 해상도 맞춤, 스크롤 스크럽, 한 번만 실행되는 등장 트리거, 숫자 카운트, 안내판 글자 넘김)는 `assets/motion-kit.js`에 있으니 페이지 `<script>` 안에 그대로 넣어 쓴다.

순서는 다음과 같다.

1. **히어로**: PRD 제목과 핵심 가치 한 문장. 그 아래에 스크롤에 따라 Before에서 After로 바뀌는 대표 장면(sticky 스테이지)을 둔다. 장면 옆에는 같은 숫자를 보여 주는 HTML 보드를 둔다. 재생 버튼과 진행 슬라이더도 함께 둔다. 페이지가 스크롤되지 않는 환경(높이가 자동으로 늘어나는 iframe)에서도 볼 수 있어야 하기 때문이다.
2. **문제**: PRD의 문제 정의를 짧게. 문제 정의가 없으면 생략한다.
3. **기능 체인**: 의존 순서(FR-01 → FR-02 …)를 한 줄로 보여 주고, 각 칩은 해당 섹션으로 가는 링크로 만든다.
4. **기능 섹션 (기능 1개 = 섹션 1개)**: 라벨(기능 ID, 사용 화면), 기능이 하는 일을 한 문장으로 적은 제목, PRD 설명 한두 문장, 모션 장면, 조작 패널을 둔다.
5. **KPI**: Before와 After를 보여 준다. PRD에 예시값이라고 적혀 있으면 그대로 `예시`를 붙인다.
6. **로드맵 / 의사결정 포인트**: PRD에 있을 때만 둔다.

### 5. 장면을 기능에 붙이는 규칙

이 규칙들이 "기능을 잘 반영했다"의 기준이다.

- **조작하면 결과가 바뀐다.** 슬라이더, 토글, 버튼, 선택 중 하나로 그 기능의 입력을 바꾸면, 장면과 숫자가 그 기능의 논리대로 바뀐다. 아무 버튼이나 눌러서 애니메이션만 다시 재생되는 것은 조작으로 치지 않는다.
- **기능끼리 연결한다.** PRD에 의존 관계가 있으면 상태를 공유한다. 앞 기능의 출력이 뒤 기능의 입력이 되게 한다. 예를 들어 인력을 늘리면 혼잡 경보가 꺼지고, 데이터 소스를 끄면 뒤 기능이 "대기"로 바뀐다. 공유 상태 객체 하나와 구독 함수 목록(`S.subs`)으로 구현한다.
- **PRD의 고유명사를 화면에 쓴다.** 화면 이름(S-01 등), 구역 이름, 시스템 이름, 사용자 유형을 그대로 라벨로 쓴다.
- **점 하나에 의미를 준다.** 파티클을 쓰면 그 점이 무엇인지(여객 1명, 주문 1건, 데이터 레코드 1개) 캡션으로 밝히고, 가능하면 개수를 PRD 수치와 1:1로 맞춘다.
- **계산은 단순하고 정직하게 한다.** 예상 대기 = 인원 ÷ 처리 용량처럼 설명할 수 있는 식을 쓰고, 화면에 "단순 추정"이라고 적는다.
- **첫 화면만 봐도 의미가 통한다.** 모든 섹션은 애니메이션 전에도 읽을 수 있는 상태로 시작한다. `opacity:0`에서 시작해서 관찰자를 기다리게 하지 않는다. 등장 모션은 한 번만 실행한다.
- **등장 모션은 화면 상태만 바꾼다.** "처음엔 끊겨 있다가 하나씩 연결되는" 연출이 필요하면, 공유 상태는 완성 상태로 두고 그 장면 안의 표시용 변수(`shown`)만 잠깐 되돌렸다가 재생한다. 공유 상태를 되돌리면, 사용자가 메뉴 링크로 뒤 섹션에 뛰어갔을 때 그 섹션이 잠깐 "연결 필요"로 깜빡인다.
- **의존 기능이 꺼지면 이유와 해결 버튼을 보여 준다.** 앞 기능의 입력이 꺼져 뒤 기능이 동작할 수 없으면, 섹션 위에 "FR-01에서 ○○ 연결 필요"와 [연결하기] 버튼을 띄운다. 기능 사이의 의존 관계가 눈에 보이게 하는 장치다.
- **KPI 옆에 시뮬레이션 값을 섞지 않는다.** 장면에서 계산한 값(예: 주행거리 −74%)은 그 기능 섹션에만 둔다. KPI 섹션은 PRD 값만 보여 준다. 지표 이름이 같아도 측정 방법이 다르면 오해를 부른다.

### 6. 기술 규칙

- 파일 맨 위에 `<meta charset="utf-8">`과 viewport를 둔다(스켈레톤에 있음). 로컬 파일로 열 때 한글이 깨지지 않게 하기 위해서다.
- 공유 상태의 구독 함수는 의존 순서대로 등록하고, 첫 실행은 스크립트 맨 끝의 `S.emit()` 한 번에 맡긴다. `MK.store`는 구독 함수마다 오류를 따로 잡으므로, 한 모듈이 실패해도 나머지는 계속 동작하고 콘솔에 `[prd-motion]` 오류가 남는다.
- 반투명 색은 `color-mix(in srgb, var(--토큰) 16%, transparent)`로 쓴다. rgba 숫자를 박아 두면 밝은 테마로 바꿀 때 하나하나 고쳐야 한다. 캔버스에서는 `MK.rgba(MK.token('warn'), .3)`을 쓴다.
- 라이브러리 없이 Canvas 2D, SVG, CSS로 만든다. 3D가 꼭 필요할 때만 three.js를 cdnjs에서 버전을 고정해 불러온다. 대부분의 기능 장면은 2D가 더 읽기 쉽다.
- 장면별 루프는 `runWhenVisible`로 화면에 보일 때만 돌린다. 장면이 많아도 느려지지 않게 하기 위해서다.
- 스크럽 장면은 진행값 `p`(0~1)를 받아 위치를 계산하는 **순수 함수**로 만든다. 그래야 스크롤을 거꾸로 올려도 장면이 자연스럽게 되감긴다. 시간 기반 효과(흔들림, 흐르는 입자)는 그 위에 덧입힌다.
- 캔버스 글자는 좁은 화면에서 읽을 수 없게 작아진다. 화면 폭이 좁으면 긴 라벨을 줄이거나 짧은 코드로 바꾸고, 핵심 숫자는 HTML 보드에 둔다. 좁은 화면에서 의미가 사라지는 도식은 세로 레이아웃으로 바꾼다(`archetypes.md`의 합류 예시 참고).
- `prefers-reduced-motion`이면 흔들림과 자동 재생을 끄고 최종 상태를 바로 보여 준다.
- 폭 400px에서 가로 스크롤이 생기지 않아야 한다. 그리드는 `minmax(0,1fr)`을 쓰고 좁은 화면에서는 한 줄로 쌓는다.

### 7. 출력과 확인

- 파일 하나(`<제품명>-motion.html` 같은 이름)로 저장한다. Artifact 도구가 있으면 publish해서 링크를 준다. 이때 Artifact의 페이지 규칙(디자인 스킬, CDN 허용 목록, 테마 규칙)을 함께 따른다.
- 넘기기 전에 스크립트 문법을 한 번 검사한다. 예: `<script>` 내용을 파일로 빼서 `node --check`.
- 가능하면 렌더링된 화면을 한 번 보고, 고칠 것이 있으면 한 번만 고친다.
- 사용자에게는 기능별로 "어떤 모션이고, 무엇을 조작하면 무엇이 바뀌는지"를 표로 보고한다. PRD에 없어서 예시로 채운 값이 있으면 그 목록도 알린다.
